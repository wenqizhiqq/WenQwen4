**软件定位**

WenQwen 是一个完全离线的工业 AI 助手，目标是在不联网的工控机上，基于本地 GGUF 大模型和本地资料回答问题。它不做模型训练，也不依赖云端 API，推理、知识检索和对话记忆全部在本机完成，适合设备现场、保密车间等不能联网的场景。

**运行形态**

项目为 .NET 8（net8.0-windows）单工程程序，输出类型是控制台 Exe，仅借用 WinForms 的 MessageBox 做提示。精简后只剩两个源文件：`LocalChatAssistant.cs` 承担入口和全部业务，`ModelLocator.cs` 负责模型定位。启动时设置 UTF-8 控制台编码，打印“正在加载模型”，确认模型可用后加载 GGUF 并进入问答循环。

**模型定位与加载**

默认模型是 `D:\wqz\models\qwen2.5-vl-3b-instruct-q4_k_m.gguf`。若默认路径不存在，ModelLocator 先在各盘浅层目录按同名文件广度搜索，深度 3，跳过 Windows、Program Files、AppData、node_modules 等目录，单盘限 4 秒、总计 10 秒，非系统盘优先；仍找不到则退化为查找文件名含 qwen 的最大 `.gguf`；再失败才弹窗并允许手工输入路径，最终仍不存在则退出。定位到文件后还有一道体检：先打印路径和体积，再读前 4 字节确认文件头是 `GGUF`；小于 64MB 或文件头不对会直接给出“文件不完整 / 格式不对”的提示并退出，避免 llama.cpp 统一抛出的 `Failed to load model` 掩盖真实原因（网盘边下边读、下载中断、占位文件都会走到这一步）。加载参数为上下文 8192、线程数等于 CPU 核数、GpuLayerCount 为 99，但实际引用的是 LLamaSharp 的 CPU 后端，因此只能 CPU 推理。3B Q4_K_M 模型约 1.8GB，运行时内存约 2 到 3GB，加载和生成速度明显快于 7B。当前只用其文本能力，视觉投影文件 `mmproj-qwen2.5-vl-3b-instruct-q8_0.gguf` 未加载，图片输入不生效。

**知识库（RAG）**

程序从当前目录的“资料”文件夹递归读取 txt、md、csv、docx、doc、xlsx、xls、pdf 文件，按格式抽取纯文本后再分块：docx 用 OpenXml 按段落顺序取正文与表格文字，xlsx 走 OpenXml 并还原共享字符串，每一行都拼成“表头=值”的自描述文本（否则小模型会看串列，把加减速时间当成速度答出来），空单元格按列号对齐不会让整行错位；pdf 用 iTextSharp 逐页取字，旧版 doc 按 UTF-16 解码后只保留可读片段，txt/md/csv 直接按 UTF-8 读。抽取时会丢掉目录域代码（PAGEREF）、纯页码、连续重复的页眉页脚，短于 40 字的碎片不建块，正文按段落累积到 800 字一块。单个文件解析失败会被跳过，启动时打印跳过清单，PDF 扫描件因无文字层也会进入跳过清单，chm 不在支持范围。

**问答与推理**

主循环中，输入 exit 退出、clear 清空记忆；输入纯数字且等于上一轮编号时，自动追问“请详细解释：上一问题”；其余输入作为新问题。检索分三步：先把问题切成英文/数字型号词加中文二元组（中文没有空格，按字切二元组才能命中），去掉“怎样、怎么、什么、如何、等于、多少”等泛词；再按词频、词稀有度给块打分，汉字占比低的代码片段降权；最后先按文档排序（文件名命中查询词额外加高分，因此以主题命名的文档会优先），第一名明显领先（超过第二名 1.5 倍）时只带这一篇，否则带前两名各 2 块、总计不超过 3000 字。不带第二篇是为了防止小模型串题——实测问“AL-51 报警”时，附带另一篇回零文档会让它答成“回零方向设置错误”。提示词使用 Qwen 的 `im_start` 模板，资料放进 user 消息而不是 system（小模型对 system 里的长文本不敏感），且不拼接历史问答：3B 会把上一轮答案原样抄进新答案，问齿轮比却先复述回零处理。系统提示要求只依据资料回答、资料没写就说“资料中没有提到”、标注来源文件名，并明确“只答相关内容，不要整段抄录”。推理用 `StatelessExecutor`，每次重新吃整段提示词并自行清空 KV 缓存；此前用 `InteractiveExecutor` 复用同一实例，第二轮起会直接吐 EOS 导致空回答。采样为温度 0.3、TopK 40、TopP 0.9、重复惩罚 1.18（惩罚窗口 128 token）、频率/存在惩罚 0.2，最大 600 token，遇到 `im_end`、`User:` 等标记停止；低温度且无重复惩罚时 3B 会把同一段“现象/处理”反复刷屏到上限。

**从零构建（仓库里没有 bin）**

仓库只保存源码——`WenQwen/LocalChatAssistant.cs`、`WenQwen/ModelLocator.cs`、`WenQwen/WenQwen.csproj` 与解决方案文件，`bin/` 和 `obj/` 都在 `.gitignore` 里，从不入库：它们只是编译产物，几万个 DLL 里绝大部分是各平台原生库，提交上去既超 GitHub 单文件 100MB 限制又毫无价值。克隆后跑一条命令即可自动还原并生成：

```powershell
git clone <仓库地址> WenQwen2
cd WenQwen2
.\build.ps1            # 还原依赖 + 编译，产物落在 WenQwen\bin\Debug\net8.0-windows
.\build.ps1 -Run       # 编译完直接启动
.\build.ps1 -Clean     # 先删 bin/obj 再重建
```

脚本会检查 .NET SDK、打印版本、构建后汇报产物路径 / 文件数 / 总大小，并把仓库根目录 `资料\` 里的知识文件同步到运行目录、自动补建「资料」文件夹。若机器策略禁止执行 PowerShell 脚本，等价的一条命令是 `dotnet build WenQwen\WenQwen.csproj -c Debug`。

**资料（知识库）目录**

知识文件统一放**仓库根目录**的 `资料\`（txt / md / csv / docx / doc / xlsx / xls / pdf），这是唯一需要维护的地方，`.gitignore` 只放行根目录这一个 `资料`；`bin` 下运行目录里的副本是构建时拷过去的，随 `bin` 一起被忽略，不入库。每次 `build.ps1` 会把根目录 `资料\` 里的文件（跳过占位的 `.gitkeep`）复制到 `WenQwen\bin\<配置>\net8.0-windows\资料\`，所以克隆仓库 → 构建 → 启动，知识库就自动就位；直接 `dotnet run` 时工作目录是仓库根，程序会直接读根目录的 `资料\`。复制是增量覆盖，不会删除运行目录里多出来的文件。工程已锁定 `RuntimeIdentifier=win-x64`、`SelfContained=false`，因此只会拷贝本机需要的原生库，输出约 420MB（其余是 TorchSharp 的 `torch_cpu.dll`、OpenCvSharp、onnxruntime 等未被当前功能引用的包，可按需继续精简）。没装 SDK 时脚本会提示去 `https://dotnet.microsoft.com/download/dotnet/8.0` 安装。GGUF 模型不入库，见下一节由程序自动定位。

**部署与使用**

把模型放在任意磁盘的浅层目录即可，文件名保持不变；把要学习的文件放进**仓库根目录**的「资料」文件夹（构建时会自动同步到运行目录；也可直接放进运行目录下的「资料」），启动后会自动加载并列出已学习文件。机器需安装 .NET 8 运行时。首次启动要花数秒到数十秒加载模型，之后按提示输入问题即可。llama.cpp 的原生日志（KV cache、计算图层数、缓冲区分配等）默认全部静默，控制台只留程序自己的提示；需要排查模型加载问题时设 `WENQWEN_DEBUG_LLAMA=1` 再运行。对话只保存在当前进程内，退出即丢失。

**现状与局限**

优点是零联网、部署简单、入口单一；模型缺失能自动跨盘查找，容错比原来好；docx/xlsx/pdf 都能真正解析，表格按“表头=值”还原；每问都是独立的无状态推理，不会再出现第二轮起空回答。局限也很明显：检索仍是字面命中，只按二元组和词频排序，换个说法（如“连不上”对“通讯失败”）就可能漏检，需要向量检索才能解决；会话历史不再进入提示词，纯闲聊式上下文追问能力因此变弱；知识库每次启动重建，没有持久化；扫描件 PDF 没有文字层、chm 无法解析；3B 模型仍会漏答细节或把半句说完就停，例如把表格某一列读错、把 G02 的 X/Y 说成“相对 Z 轴”，这类错需要人工核对来源文件；CPU 后端下 3B 模型吞吐仍受单机限制，一问通常数秒到十几秒；控制台交互没有并发和会话管理；工程里仍保留 OpenCvSharp、TorchSharp、Whisper、NAudio 等与现有功能无关的包，可以继续精简。总体看，这是一个可用的本地工业知识问答原型；若要产品化，应优先补向量检索、历史裁剪和图形界面。
