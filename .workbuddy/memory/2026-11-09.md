## 修复：知识库检索答不出（用户截图：8 个 docx、1785 块，问 modbus 一律“知识库中没有相关信息”）
根因三条：
1. docx 被当二进制纯文本读 → 1785 块全是乱码，等于没有资料。
2. 中文没有空格，旧检索按空格/标点切词，整个问题被当成一个词去 Contains，必然 0 命中。
3. 模型停止条件把 token 计数写成了 `count++ > limit`（先自增后判），逻辑混乱；提示词把长资料塞进 system，3B 不跟。

改法（均在 `WenQwen/LocalChatAssistant.cs`）：
- 按格式抽文本：docx 用 OpenXml（段落顺序，含表格）、xlsx 用 OpenXml（还原 SharedString）、pdf 用 iTextSharp 逐页、doc 用 UTF-16 兜底、txt/md/csv 直读；跳过清单带异常类型。
- 抽文本时去噪：丢 PAGEREF/HYPERLINK/TOC 域代码、纯页码、连续重复行；<40 字碎片不建块；按段落累积到 800 字一块。
- 检索：英文/数字词 + 中文二元组分词；`QueryStopWords` 去泛词；词权重 = (1+ln(N/(df+1)))×1.5(ASCII)；块打分加词频对数压制、代码块（汉字占比<0.15）降权 0.5；**文档级排序**——文件名命中查询词额外 +5×weight，先取前 2 个文档再各取 2 块，总预算 3000 字，代码块最多带 1 块。
- 提示词：资料搬到 user 消息（system 只留角色+约束），要求只依据资料、注明来源；空回答自动换 0.6 温度重试一次。
- `Console.IsInputRedirected` 时把 InputEncoding 设 UTF-8（否则管道喂中文按 GBK 解码变乱码，这是我测试踩的坑）。
- 调试开关：`WENQWEN_DEBUG_RAG=1` 打印分词/命中块/加载字数，`WENQWEN_DEBUG_PROMPT=1` 导出提示词与 token 数/停止原因到 %TEMP%。

### 本轮修掉的三个真 bug
1. **第二轮起全是空回答**：`InteractiveExecutor` 复用同一实例，第一问后把问答残留在会话状态里，第二问起 `InferAsync` 一个 token 都不出（`[INF] tokens=0`）。改为 `StatelessExecutor`（每次重吃整段提示词、自管 KV 缓存），删除 `_context` 字段。注意 0.26 里 `StatelessExecutor` 不实现 `IDisposable`，不能 `?.Dispose()`。
2. **串题**：参考资料带两篇时，问“AL-51 报警”答成另一篇的“回零方向设置错误”。加主导文档规则——第一名分数 ≥ 第二名 ×1.5 时只带这一篇。
3. **表格读串列**：TSV 平铺后小模型把“加减速时间 300”答成“速度是 300”。xlsx 抽取改为每行 `表头=值 | 表头=值`，并用 `CellReference` 算列号，空单元格不再错位。

## 静默 llama.cpp 原生日志（用户截图：满屏 llama_kv_cache / graph_reserve / llama_context）
- 根因：LLamaSharp 默认把 llama.cpp 的原生日志转发到控制台 stderr，用户看到的是 KV cache 每层设备、图节点数、CPU 计算缓冲 300.75MiB 这类内部细节。
- 改法：Main 开头调用新增的 `SilenceLlamaLog()`，用 `LLama.Native.NativeLogConfig.llama_log_set((level, message) => { })` 全部静默；设 `WENQWEN_DEBUG_LLAMA=1` 时改为输出到 stderr。lambda 直接传给方法参数以省略 level 的枚举类型名（0.26 的 `LLamaLogCallback` 是嵌套委托，类型名不在 XML 文档里）。
- 验证：stdout/stderr 分开捕获，加载+一问运行后 stderr 0 行、stdout 28 行全是程序自身提示，问答正常。
- 坑：之前所有测试都写 `2>$null`，所以一直没发现这堆日志；以后测控制台输出要分开捕 stdout/stderr。
